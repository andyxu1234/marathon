# 马拉松赛事数据抓取方案

> **版本**: v1.0  
> **更新**: 2026-08-28  
> **状态**: 已实现并验证通过

---

## 1. 背景与目标

### 1.1 原方案问题

此前通过 AI Agent 定时任务生成 Markdown 文件来填充赛事数据，存在以下问题：

| 问题维度 | 具体表现 |
|---------|---------|
| 准确性 | AI 生成的赛事信息未与原始数据源交叉验证，存在幻觉 |
| 及时性 | 定时任务频率固定，无法按数据源重要性差异化调度 |
| 完整性 | 单一来源无法覆盖所有赛事，缺失信息无补漏机制 |
| 可审计 | 原始数据未留存，无法回溯字段来源和修改历史 |
| 可控性 | 全自动写入，缺少人工审核开关 |

### 1.2 设计目标

- **多源采集**：支持多个数据源并行抓取，按权重投票合并
- **确定性优先**：90% 流程由确定性代码完成，AI 仅作为解析兜底
- **人工审核开关**：可全局开启/关闭，低置信度数据进入待审核队列
- **完整审计链**：所有原始数据留存（URL + 抓取时间 + HTML 快照 + 哈希）
- **插件式扩展**：新增数据源只需实现 `BaseSourceAdapter` 接口并注册

---

## 2. 技术架构选型

### 2.1 为什么不用多 Agent 框架（AutoGen / CrewAI / LangGraph）

| 对比维度 | 多 Agent 框架 | 本方案（混合管道） |
|---------|-------------|----------------|
| 确定性 | ❌ 非确定，同一输入可能不同输出 | ✅ 规则解析 100% 确定性 |
| 调试成本 | ❌ 多 Agent 交互链路长，难以定位 | ✅ 每个 Stage 独立可测 |
| 延迟 | ❌ 每步需 LLM 调用，累计 30s+ | ✅ 规则解析 < 1s，AI 仅兜底 |
| 成本 | ❌ 每次运行消耗大量 token | ✅ 仅异常页面调 LLM |
| 适用场景 | 非结构化创意任务 | ✅ 结构化数据提取与清洗 |

**结论**：数据管道是确定性任务，用多 Agent 框架属于过度设计。AI 仅在规则解析失败时作为兜底，处理非结构化页面。

### 2.2 技术栈

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| 后端框架 | FastAPI + SQLAlchemy async | 异步 I/O，高并发 |
| 调度器 | APScheduler (AsyncIOScheduler) | 支持 cron 表达式，防重入 |
| HTTP 客户端 | httpx (async) | 异步抓取，支持重试 |
| HTML 解析 | BeautifulSoup4 + lxml | CSS Selector + 正则 |
| 模糊匹配 | RapidFuzz | 名称相似度计算（Levenshtein） |
| 重试机制 | Tenacity | 指数退避重试 |
| 数据库 | MySQL | 存储正式赛事 + 原始数据 + 待审核 |
| AI 兜底（可选） | OpenAI 兼容 LLM API | 仅规则解析为 0 条时调用 |

## 4. 核心模块详解

### 4.1 数据类定义 (`base.py`)

管道各阶段间流转的数据类采用 Python `dataclass`：

```
RawPage          → 采集到的原始 HTML 页面
  ↓
EventCandidate   → 规则/AI 解析出的候选赛事（字段未标准化）
  ↓
NormalizedEvent  → 归一化后的赛事（日期/city/枚举已统一）
  ↓
MergedEvent      → 多源合并后的最终赛事（含冲突报告）
```

**关键字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `source_weight` | int (0-100) | 来源权威度，影响合并投票权重 |
| `parse_confidence` | int (0-100) | 解析置信度，rule=60-85, ai=75 |
| `parser_tag` | str | 解析方式标记：`rule` / `ai` |
| `matched_event_id` | int? | 非 None 表示更新已有赛事 |

### 4.2 Source Adapter 接口 (`base.py`)

新增数据源只需继承 `BaseSourceAdapter` 并实现两个方法：

```python
class BaseSourceAdapter(ABC):
    source_name: str           # 来源名称
    source_weight: int         # 权威度权重 (0-100)
    schedule_cron: str         # 调度频率 cron 表达式

    @abstractmethod
    async def fetch_raw(self, timeout: int = 20) -> list[RawPage]:
        """抓取原始页面"""
        ...

    @abstractmethod
    def parse_rule_based(self, raw: RawPage) -> list[EventCandidate]:
        """规则解析：CSS/XPath/正则提取。无法解析返回空列表"""
        ...

    def parse_ai_fallback(self, raw: RawPage) -> list[EventCandidate]:
        """AI 兜底解析：默认不做，有 AI 服务时子类可覆盖"""
        return []
```

**注册方式**：在 `sources/__init__.py` 的 `REGISTRY` 列表中添加实例即可：

```python
REGISTRY: list = [
    ZuicoolAdapter(),      # 权重 80, 每 2 小时
    RunchinaAdapter(),     # 权重 100, 每 2 天 (SPA 降级)
    WebSearchAdapter(),    # 权重 45, 每天
]
```

### 4.3 解析层 (`parser.py`)

采用**规则优先，AI 兜底**策略：

```
对每个 RawPage:
  1. 调用 adapter.parse_rule_based(page) → 命中则使用，跳过 AI
  2. 规则解析为 0 条 且 PIPELINE_AI_FALLBACK=True 且 LLM_API_KEY 已配置
     → 调用 LLM 提取赛事信息 (temperature=0, response_format=json_object)
  3. 两种方式都解析不出 → dropped_pages += 1
```

AI 兜底的 Prompt 设计要点：
- 明确指定输出 JSON 数组格式，禁止额外说明文字
- 限定字段枚举值（如 `type_raw` 只能是 `马拉松/半程马拉松/健康跑/越野跑/其他`）
- 截断 HTML 文本到 12000 字符以防超长
- AI 解析的 `parse_confidence` 固定为 75（低于规则解析的 60-85）

### 4.4 清洗归一化层 (`normalizer.py`)

**日期解析**：支持 3 种正则模式自动匹配

| 格式 | 示例 | 正则 |
|------|------|------|
| 标准分隔 | `2026-09-20` / `2026/09/20` / `2026.09.20` | `20\d{2}[\-/.年]\d{1,2}[\-/.月]\d{1,2}` |
| 中文日期 | `2026年9月20日` | `20\d{2}年\d{1,2}月\d{1,2}日` |
| 无年份 | `9月20日` → 自动补当年/次年 | `\d{1,2}月\d{1,2}日` |

**城市/省份映射**：内置 40+ 城市到省份的映射表，支持「杭州萧山」→「杭州市」这种包含匹配。

**枚举标准化**：

| 字段 | 原始值示例 | 标准值 |
|------|-----------|--------|
| event_type | "全马"/"全程"/"马拉松" | 1 |
| event_type | "半马"/"半程" | 2 |
| event_type | "健康跑"/"欢乐跑"/"5K" | 3 |
| event_type | "越野"/"山地" | 4 |
| event_level | "白金"/"白金标"/"WMM" | 1 |
| event_level | "金标"/"金" | 2 |
| event_status | "报名中"/"报名开启" | 2 |
| event_status | "抽签中" | 2 (归入报名中) |
| event_status | "报名结束"/"报名截止" | 3 |

**状态倒推**：优先用日期判断状态（比文本关键字更可信）
- 开赛日 < 今天 → 已结束 (5)
- 开赛日 ≤ 明天 → 比赛中 (4)
- 今天 ≤ 报名截止 → 报名中 (2)
- 今天 > 报名截止 → 报名结束 (3)

### 4.5 去重合并层 (`dedupe.py`)

**三层去重策略**：

```
Step A: 精确指纹分组
  fingerprint = MD5(name_key + date(YYYY-MM-DD) + city)
  name_key = 去空格/小写/去通用后缀(马拉松/半程/半马/全马)

Step B: 模糊合并 (并查集)
  两两比较：fuzz.ratio(name_a, name_b) ≥ 90
           + 日期相同（或都无日期）
           + 城市相同（或一方无城市）
  → 合并为同一赛事

Step C: 加权投票
  对每个字段：
    score = source_weight × (parse_confidence / 100)
    按值分桶累加 score → 最高分桶的值为 winning_value

Step D: 冲突检测
  有 ≥ 2 个不同值桶 且第二名 score ≥ 第一名 × 50% → 标记冲突
  每个冲突字段扣 5 分置信度（最多扣 40）
```

**合并后置信度计算**：

```
base_conf = avg(source_weight × confidence) 对组内所有来源
final_conf = max(0, base_conf - min(40, conflict_count × 5))
```

### 4.6 分流入库 (`runner.py`)

```
对每个 MergedEvent:
  ├─ require_review = False → 直接入 mi_event (新增或更新)
  │
  └─ require_review = True:
      ├─ confidence ≥ threshold (75) 且无冲突 → 自动入库
      ├─ confidence < threshold → 写入 mi_event_pending (待审核)
      └─ 有冲突 且 confidence < threshold+10 → 写入 mi_event_pending
```

**入库逻辑**：
- **新增**：`matched_event_id is None` → INSERT 到 `mi_event`
- **更新**：`matched_event_id is not None` → 只覆盖非 None 字段，无变化则 skip
- **待审核**：写入 `mi_event_pending`，保留 `conflict_details` JSON 供人工查看

### 4.7 调度器 (`scheduler.py`)

```python
class PipelineScheduler:
    _scheduler: AsyncIOScheduler   # APScheduler 实例
    _running: bool                  # 防并发重入标志
    _last_report: PipelineReport    # 最近一次执行报告
    _run_history: list[dict]        # 最近 20 次执行历史
```

**关键配置**：
- `coalesce=True`：错过的执行只补跑 1 次
- `max_instances=1`：同一 job 不并发
- `misfire_grace_time=600`：10 分钟内的错过仍然执行
- `timezone="Asia/Shanghai"`：时区固定为北京时间

**防重入**：`_running` 标志确保全管道同一时间只跑一个实例。

## 5. 数据源说明

### 5.1 数据源总览

| 数据源 | 类名 | 权重 | 频率 | 状态 | 说明 |
|--------|------|------|------|------|------|
| 最酷 ZUICOOL | `ZuicoolAdapter` | 80 | 每 2 小时 | ✅ 正常 | 主要数据来源，HTML 可直接解析 |
| 中国马拉松官网 | `RunchinaAdapter` | 100 | 每 2 天 | ⚠️ 降级 | Vue SPA + 验证码，普通请求无法获取内容 |
| 搜索引擎补漏 | `WebSearchAdapter` | 45 | 每天 1 次 | ✅ 正常 | Bing 搜索「马拉松 报名 2026」等关键词 |

### 5.2 最酷 ZUICOOL (`zuicool.py`)

**采集 URL**：
- 首页：`https://zuicool.com`
- 新闻页：`https://zuicool.com/news`

**解析策略**：
1. **新闻页**：遍历 `<a>` 标签，筛选含「马拉松/报名/开赛/抽签」关键词的标题
2. **首页卡片**：CSS Selector 匹配 `div[class*='card']`, `li[class*='item']`, `a[class*='event']`，提取标题 + 日期 + 城市 + 费用
3. **正则提取**：日期、城市、费用、赛事类型（全马/半马/健康跑/越野）
4. **名称清洗**：去除「开启报名」「抽签结果」等后缀，去除括号内容

**重试机制**：Tenacity 指数退避，最多 2 次，仅重试网络异常。

### 5.3 中国马拉松官网 (`runchina.py`)

**问题描述**：
- 网站 `runchina.org.cn` 使用 Vue SPA + 腾讯防水墙验证码
- 普通 HTTP 请求只能拿到 `<div id="app"></div>` 空壳
- 无法获取赛事数据

**降级策略**：
- 检测 SPA 特征（`<div id="app">` + `static/index-`）→ 立即返回空列表
- 检测验证码特征（`TEOCaptcha` / `AliyunCaptcha`）→ 立即返回空列表
- 降低调度频率：每 2 天凌晨 3 点尝试 1 次（万一改版为 SSR 仍能抓到）
- 预留 Playwright 集成入口（`_fetch_with_playwright`，未启用）

**替代方案**：由 `WebSearchAdapter`（搜索引擎补漏）覆盖中田协的信息。

### 5.4 搜索引擎补漏 (`websearch.py`)

**搜索关键词**：
```
"马拉松 报名开启 2026"
"马拉松 抽签 公布 2026"
"马拉松 赛事 日程 2026"
"半程马拉松 报名 2026"
```

**解析策略**：
- 请求 Bing 搜索（无 API Key，纯 HTML 解析）
- 解析 `<li class="b_algo">` 搜索结果项
- 提取标题（`h2 a`）+ 摘要（`.b_caption p`）
- 从标题 + 摘要组合文本中正则提取日期、城市、类型、状态

**置信度**：45（搜索结果可信度较低，仅作交叉验证和补漏）

### 6.2 与正式表 `mi_event` 的关系

```
mi_event_source (原始数据)
       │
       │ 合并去重
       ▼
mi_event_pending (待审核) ──审核通过──→ mi_event (正式赛事表)
       │
       │ 置信度足够
       ▼
mi_event (正式赛事表)
```

- `mi_event_source` 每条原始采集记录都留存，`match_status` 跟踪匹配结果
- `mi_event_pending` 存放低置信度/冲突数据，审核通过后写入 `mi_event`
- `mi_event` 是前端展示的唯一数据源

```python
        # 实现抓取逻辑
        ...

    def parse_rule_based(self, raw: RawPage) -> list[EventCandidate]:
        # 实现解析逻辑
        ...
```

### 10.2 接入 AI 兜底

1. 在 `.env` 中配置 `LLM_API_BASE`、`LLM_API_KEY`、`LLM_MODEL`
2. 设置 `PIPELINE_AI_FALLBACK=true`
3. 规则解析为 0 条的页面将自动调用 LLM 提取
